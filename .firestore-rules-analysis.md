## Tutor notes update (2026-09-18)

- The student's detail page now has a Notes tab; writing there constitutes class note-taking without a separate session state.
- `personalPractice/{studentId}` now allows get/create/update by linked teachers as well as its student. `practiceItems` and knowledge events retain their previous owner-only permissions.
- `teacherNotes/{teacherId}_{studentId}` stores immutable-origin class copies (`items`, max 500) and editable `privateText` (max 20000), plus IDs and server `updatedAt`. Only that linked teacher can get/create/update; students, other teachers, listing and deletion are denied. The client subscribes to a single known document, not a query.
- One transaction appends class lines with identical IDs and `addedBy: TUTOR` to both destinations. The teacher never edits the student's existing lines through this UI. Students may edit/delete their copies without changing the teacher's archive.
- Student sync now applies changed/deleted IDs in a transaction, preserving concurrent teacher additions. A subscription delivers online additions to an open student notebook. Drafts use their original baseline so incoming lines are not interpreted as deletions. For conflicting student edits to the same ID, the last committed change wins.
- Trust boundary: list element schemas and `addedBy` are not enforced per element by rules; a linked teacher is authorized to modify the student's whole practice document. Private observations are protected by a separate document and immutable ownership checks on update.

- `users/{uid}`: client gets its own profile; backend creates it; client may later update only `displayName`.
- `teacherInvites/{code}`: personal, single-use invitation. Teacher creates it (with their own profile name) and lists with `where("teacherId", "==", uid)`. Direct `get` supports the explicitly public `/join/{code}` preview while active; once used, only its teacher and the student who used it can read it. Teacher deletes only unused invitations.
- `teacherStudents/{teacherId}_{studentId}`: the student creates it in the same batch that consumes the invitation (`active:false, usedBy, usedAt`). Student lists with `where("studentId", "==", uid)`; teacher lists with `where("teacherId", "==", uid)`. No groups.
- `studentProgress/{uid}` and `studentProgress/{uid}/events/{id}`: written only by the student (finished stories, last story opened, saved word ids, practice sessions). Read by the student and by teachers with a `teacherStudents` link. `finishedStories`/`lastStory` and `savedWords` are written by two independent client-side syncers (`components/visual/reading-memory.ts` and `components/accounts/ProgressSync.tsx`), each `merge:true` on its own disjoint fields, so they can't race on the same key.
- `personalPractice/{uid}` and `practiceItems/{uid}`: written only by the student (hand-typed practice notes, words saved while reading). Owner-only, not teacher-readable — unlike `studentProgress`, these were judged private study material rather than a teacher-facing summary. Item shape is trusted client-side (same paranoid parser as the equivalent localStorage repository); rules only bound the list's size, since Firestore rules can't validate per-element shape inside a list of maps.
- `studentKnowledge/{uid}/events/{eventId}`: written only by the student, one immutable document per lexical-knowledge event (doc id = `eventId`, so a client can never overwrite an existing event, only add new ones). Owner-only read, no teacher access. `occurredAt` is the one timestamp in the whole schema that isn't pinned to `request.time` — it has to reflect when the interaction happened (it drives spaced-repetition scheduling), not when it reached the server, so it's accepted within a bounded tolerance window (±10 minutes ahead, no earlier than 2024) instead of exact equality. That is a deliberate, narrower trust boundary than the rest of the schema: a student's client controls this timestamp within that window.
- `teacherTasks/{taskId}`: teacher-owned immutable assignment: `kind` (`story`, `flashcards`, `verbs`), bounded title, a strict content map, start/due timestamps and server timestamp. The teacher lists only tasks with their own `teacherId`; an assigned student can only get a known task.
- `teacherTasks/{taskId}/assignees/{studentId}`: individual recipient copied from an existing `teacherStudents` link. The teacher creates/removes it; its student reads it through a collection-group query filtered by their own UID. There is no completion document: the UI derives completion from the student's synchronised progress, so a student cannot set a result directly.
- Auth: Firebase email/password and Google. Authorization reads the immutable Firestore `role`; profile PII remains owner-only.
- Default deny covers all other paths and operations.

## Rule attack review

- Public listing: denied for users, invitations (except the teacher's constrained query), progress, practice notes/items, knowledge events and tasks. A student task collection-group query is allowed only when `studentId == request.auth.uid`.
- Cross-account read/write: tests deny another teacher's invitations/progress and an unassigned student's task. Task recipients must already be linked to the task's teacher. Practice notes/items and knowledge events deny both cross-account writes and any read by someone other than the owning student (including that student's own teacher).
- Role, ownership and immutable-field bypass: tests deny role changes and teachers creating a task whose `teacherId` belongs to someone else. Task documents have no update path; a task recipient cannot add another recipient or create a completion marker. Knowledge events have no update path either, so a client can append new evidence but never edit or delete a past one.
- Schema and range validation: users, invitations, links, progress events, practice notes/items, knowledge events, tasks and assignees use allow-lists and bounded strings/lists. Task kind and content-map shape are coupled; dates are timestamps and `dueAt >= startsAt`. Knowledge events additionally require the document id to equal the event's own `eventId` and `learnerId` to equal `'user:' + studentId`, so a client can't attribute an event to a different learner than the path it's writing to.
- Batched integrity: consuming an invitation requires a link in the same batch. Creating task recipients validates the parent task with `getAfter`, so a batch cannot attach a recipient to a task owned by another teacher.
- Remaining product trust boundary: students may write only their own progress, practice data and knowledge events, but it is self-reported browser activity. This prevents cross-account access, not a student who intentionally falsifies their own learning data — knowledge events add one more degree of self-reported trust by accepting a client-chosen `occurredAt` (within a bounded window) rather than the server's own clock, because the spaced-repetition math needs the real interaction time, not the sync time.
